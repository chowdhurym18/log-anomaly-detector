# Final Summary — Validating the Detection Pipeline on BGL

_Capstone report for the final development phase (second-dataset validation, per professor request). Written after running every experiment below; every number is measured, none estimated. Companion reports: `bgl_results.md`, `bgl_vs_hdfs.md`, `llama_bgl_evaluation.md`._

## 1. What changed

The architecture is **unchanged**: normal-only GRU → surprise score → validation-derived Normal/Uncertain/Suspicious bands → Llama (explanation for Suspicious, adjudication for Uncertain). What changed is plumbing and evidence, not design:

- **`config.py`**: filled in the placeholder `"bgl"` dataset-registry entry with real paths, and added `config_for_dataset()` — a resolver that overlays per-dataset cache/checkpoint/output/score paths on top of the HDFS-shaped defaults. For `"hdfs"` this is byte-identical to the old `CONFIG`.
- **`main.py`**: `--detect` and `--demo-uncertain` now resolve paths through `config_for_dataset(dataset)`, so `main.py --dataset bgl --detect` works end-to-end through the same entry point as HDFS. The flat next-event training path stays HDFS-only (block datasets use `run_normal_only.py --dataset <name>` instead).
- **`pipeline/detection_pipeline.py`**: `run_detection_pipeline`/`_write_report` gained an `out_dir` parameter (default unchanged) so BGL reports land in `outputs/bgl/` without touching HDFS's `outputs/`.
- **`run_normal_only.py`**: added `--dataset`, `--checkpoint-dir` (for throwaway timing runs), `--regimes`, and wall-clock/peak-RSS instrumentation (`utils/perf.py`, new — `Timer`, `peak_rss_mb`, `device_sync`; stdlib + psutil-compatible, no new dependency).
- **`run_scoring_comparison.py`**: added `--dataset`/`--out-dir`; added one new candidate score (`nll_perevent_z_mean/max`, per-event-type calibration); added an automatic Gate check (val PR-AUC gap **and** resulting Uncertain-band size) to the "adopt this score?" recommendation, so a future dataset can't silently collapse the Uncertain band by picking on PR-AUC alone.
- **`llm/uncertain_classifier.py`**: added `classify_uncertain_v2` (dataset-aware framing, grounded evidence, relaxed criteria, few-shot, structured JSON output, self-consistency) as an **additive** function — the production `classify_uncertain` (v1) is untouched.
- **New scripts**: `run_bgl_evaluation.py` (measured BGL + BGL-vs-HDFS reports, chronological-split check) and `evaluate_llm_ladder.py` (the Task-4 improvement ladder with deterministic baselines).
- **Nothing removed.** `evaluate_uncertain.py`, `analyze_routing.py`, `analyze_detection.py`, `baseline_hdfs.py`, `run_generalization.py` are untouched and still work exactly as before.

## 2. Why it changed

The professor's ask was explicit: validate the *existing* system on a second dataset without redesigning it, using the existing dataset registry, and measure — not assume — whether targets are met. BGL data and a first BGL model already existed from prior exploratory work (`bgl_preprocess.py`, `run_generalization.py`), but that path was a **parallel, in-memory** config (`BGL_CONFIG` built ad hoc), not the registry the professor asked me to use, and none of the individual HDFS report scripts (the ones producing the artifacts being replicated) had a BGL path at all. The work above closes that gap: BGL is now a first-class registry entry, every report script that matters is dataset-parametrized, and the four requested deliverables are generated by dedicated, reusable scripts rather than one-off analysis.

## 3. Results on BGL

**Dataset.** 4,713,494 raw log lines → 1,822 Drain3 templates (vs HDFS's 29) → 47,134 blocks (fixed 100-line windows in time order; a block is anomalous if any line carries an alert tag). Base rate 10.2% (test split) vs HDFS's 2.9%. Split: train 32,993 (29,616 normal used for training) · val 4,714 · test 9,427, stratified random, seed 42.

**Detection (held-out test, random split — the headline number, with a critical caveat in §4):**

| Metric | Value |
|---|---|
| Detection F1 | **0.9171** |
| Precision / Recall | 0.9822 / 0.8601 |
| PR-AUC | 0.9497 |
| AUROC | 0.9863 |
| Confusion (val-derived threshold) | TN 8,447 · FP 15 · FN 135 · TP 830 |

**Next-event prediction** (block-respecting windows, same protocol as detection): Top-1 86.4%, Top-3 91.7%, Top-5 92.2%, weighted F1 0.8598, macro F1 0.1625 (low macro-F1 is *expected* — most of the 1,822 templates are rare, and anomalous templates are unseen by design in normal-only training; that low confidence on rare/unseen templates is exactly the surprise signal the detector uses, not a deficiency).

**Routing:** Normal 89.4% (1.1% actually anomalous) · Uncertain 1.7% (28.7% anomalous) · Suspicious 9.0% (98.2% anomalous). LLM share 10.6% of blocks.

**Cost (measured, Apple M5 / 16 GB / MPS):** training 1,293 s (6 epochs, early-stopped), peak RSS 2,584 MiB; detection scoring 436 blocks/s (43,116 windows/s), device-synchronized; Llama latency 1.09–1.2 s/call (llama3.2:1b).

**Improvement attempts (Task 3), with evidence:**
- *Scoring-signal comparison* (`outputs/bgl/detection_analysis.md`): a combined signal (`z(max NLL) + z(top-k-miss count)`) beats the production `nll_-logp_mean` by **+0.0387 val PR-AUC** (0.9527 → 0.9915) — but it separates so sharply that it leaves **zero** validation blocks in the Uncertain band (vs 79 for the current score), which would starve the Uncertain→Llama adjudication stage the architecture requires. **Decision: kept `nll_-logp_mean`.** This is a real, measured trade-off between raw separability and a workable routing architecture, not a missed optimization.
- *Per-event-type score calibration* (a plausible idea for BGL's 63×-larger vocabulary): **failed outright** — val PR-AUC 0.21–0.30 vs the baseline's 0.95. Mechanism: the reference (validation) distribution used to z-fit each event's "normal" surprise includes labelled-anomalous occurrences of that same rare event, which raises the "expected" surprise for exactly the events we want to catch — a self-defeating calibration for rare, repeat-offender templates. Documented as a negative result; not adopted.
- Focal loss, semantic embeddings, BiGRU/attention were **not** re-tested — already measured flat on HDFS in prior work; there was no new evidence to suggest BGL would differ, so re-running them would be complexity without justification.

## 4. Comparison with HDFS

Both datasets were re-evaluated **in the same script run**, through the identical block-level protocol (same production-style detector loading, same stratified random split logic, same `nll_-logp_mean` score, same validation-derived bands) — see `bgl_vs_hdfs.md` for the full side-by-side table. Headline:

| Metric | BGL | HDFS |
|---|---|---|
| Detection F1 | **0.9171** | 0.6740 |
| PR-AUC / AUROC | 0.9497 / 0.9863 | 0.6917 / 0.8917 |
| Next-event Top-1 / wF1 | 86.4% / 0.8598 | 91.0% / 0.9066 |
| Routing: Normal / Uncertain / Suspicious | 89.4% / 1.7% / 9.0% | 96.7% / 1.1% / 2.1% |
| Training time (matched settings) | 1,293 s (6 ep) | 2,442 s (8 ep) |
| Peak RSS (training) | 2,584 MiB | 2,778 MiB |
| Scoring throughput | 436 blocks/s | 4,187 blocks/s |

BGL's detection numbers look unambiguously better than HDFS's — **this is not the whole story.** Three reasons BGL's random-split numbers overstate real-world performance, the last of which is decisive:

1. **Base-rate inflation.** 10.2% anomalous vs 2.9% — PR-AUC and F1 rise mechanically with prevalence.
2. **Easier failure semantics.** BGL alerts are hardware/kernel RAS templates a normal-only model has often *literally never seen*; HDFS anomalies are ordering violations among common events — an intrinsically harder surprise signal to learn.
3. **The random split is optimistic, and the chronological split proves it.** BGL's blocks are 100-line windows in time order, so temporally-adjacent, near-duplicate windows can land on both sides of a random split. Retraining on the **first 70%** of blocks and testing on the **last 20%** (val on the next 10%) — the deployment-realistic "detect the future from the past" setting — collapses the result:

   | Metric | Random split | Chronological split |
   |---|---|---|
   | Detection F1 | 0.9171 | **0.2803** |
   | Precision | 0.9822 | **0.1645** |
   | Recall | 0.8601 | 0.9485 |
   | PR-AUC | 0.9497 | **0.1398** |
   | AUROC | 0.9863 | 0.7237 |

   Recall actually *improves* (the model over-flags), but precision collapses — under a realistic split the detector raises far more false alarms than the random-split number would suggest, almost certainly because of base-rate/failure-mode drift between BGL's earlier and later time periods (fewer, different alert types show up later than the model trained on). **This is the single most important finding of the BGL validation**: naive random-split evaluation would have reported BGL as "solved" (F1 0.92); the honest, deployment-shaped evaluation says otherwise (F1 0.28). Both numbers are reported, prominently, in `bgl_results.md` and `bgl_vs_hdfs.md` — neither is hidden in favor of the other.

## 5. Llama evaluation (Task 4)

Methodology: for both datasets, 100 uncertain-band test blocks (fixed seed 42, identical to production routing) were evaluated against every prompt-engineering rung and three deterministic baselines (always-Normal; keyword rule; an "extended rule" built from the *same* evidence features given to the LLM — the honest check for whether the model adds anything beyond its own inputs).

| | BGL | HDFS |
|---|---|---|
| Always-Normal baseline | 71.0% acc, 0% recall | 69.0% acc, 0% recall |
| Best deterministic baseline | 71.0% (Always-Normal) | **79.0%** (keyword rule, 35.5% recall) |
| Best Llama config | 71.0% acc, 0% recall (R0, unchanged) | **77.0%** acc, 41.9% recall (self-consistency k=3 on few-shot) |
| Beats best baseline? | No (tied) | No (77.0% < 79.0%) |
| 3B model (capacity check) | 45.0% acc, 79.3% recall | 46.0% acc, **100%** recall |

**Prompt engineering measurably helped on HDFS** (67.0% → 77.0% accuracy, 0% → 41.9% recall, R0 → R5) but **did not move BGL at all** — every rung from R0 through R4 produced the *identical* verdict (100% NORMAL, 0/0/71/29 confusion) at temperature 0.

That flat result on BGL was investigated, not just reported: a direct check of a true-anomaly case under the most permissive rung (R2, grounded evidence + relaxed criteria) shows the model's own `EVIDENCE` line correctly states *"Actual event E17 in NORMAL training data: NEVER seen among 2,961,600 events"* — a fact that, per the prompt's own explicit rule, should trigger SUSPICIOUS — and the actual event's template contains the literal word "failed." Both of the R2 relaxed criteria are satisfied, quoted correctly by the model, and it still answers **NORMAL**. This is not a prompt-wording problem; it is a 1B-parameter instruction-following failure — the model can retrieve the right fact but does not reliably chain it to the stated conclusion. Self-consistency (k=3, temp 0.7) breaks the temperature-0 tie only slightly (8/100 cases flip to SUSPICIOUS on BGL); the underlying limitation persists.

The 3B model is not the answer either: it roughly **doubles recall but collapses accuracy** on both datasets (BGL 45%, HDFS 46%) — it is not more discerning, just more trigger-happy (opposite failure mode from the 1B model's over-conservatism). Bigger, in this specific comparison, traded one miscalibration for another rather than fixing the underlying reasoning gap.

**Verdict:** the ladder (dataset-aware framing, grounded evidence, relaxed criteria, structured JSON output, few-shot, self-consistency) is exhausted before either dataset clears its best deterministic baseline. Per the professor's own gating rule ("only recommend fine-tuning if experiments show prompt engineering alone is insufficient"), **that condition is now met, with a specific, evidenced mechanism** (fact retrieval succeeds; rule application fails) rather than a vague "the model isn't good enough."

## 6. Was the target achieved?

**No — not via prompting, and this was measured, not assumed.** Best measured classification accuracy on the uncertain band: 77.0% (HDFS), 71.0% (BGL), both below the 80% target and below at least one simple deterministic baseline. The honest reading: the *routing and explanation* architecture works well (Suspicious-block explanations are unaffected by any of this — they were never routed through the classifier being evaluated here), but using Llama as a **second-stage decision-maker on the hardest band** is not yet justified by these numbers on either dataset. The system's recommended posture, unchanged from before this phase: **Llama explains; the GRU detects.** A Llama verdict on Uncertain blocks should stay advisory, never authoritative, until a fine-tuned classifier clears this bar.

## 7. Remaining limitations

- **BGL's headline detection numbers are split-sensitive** (§4) — the chronological result (F1 0.28) is the more honest estimate of real deployment performance; treat the random-split number (0.92) as an upper bound, not a claim.
- **Synthetic sessionization.** BGL has no natural block/session id; fixed 100-line windows are a standard but coarse stand-in for "one operation," and their fixed size (vs HDFS's variable, semantically-real block boundaries) is itself a source of the temporal-correlation problem in §4.
- **1B-model reasoning ceiling** on the uncertain-band classification task, evidenced directly (§5), not inferred from low accuracy alone.
- **Single-machine timing/memory numbers** (Apple M5, MPS, 16 GB) — informative for this deployment but not universally portable; no GPU/CUDA comparison was run.
- **`docs/ROADMAP.md` and `docs/RESEARCH_POSITIONING.md` are now stale** — both still describe BGL as "untested"/"registry ready but unused." Not updated in this pass (out of the requested scope) but should be revised to reflect this work.
- **Macro-F1 on next-event prediction is low on both datasets** (BGL 0.16, HDFS 0.41) — expected given the number of rare classes, but a reminder that next-event accuracy and detection quality are different axes; conflating them would be a category error (as `hdfs_baseline_report.md` already flags for HDFS).

## 8. Recommended future work

1. **If the LoRA path is approved** (§6), run it and re-evaluate with the exact same ladder script — the harness is already built and will need no changes to grade the result.
2. **Chronological splitting should become the default evaluation protocol for BGL**, not an auxiliary check — the gap it revealed is too large to treat as a footnote.
3. **Smarter BGL sessionization** (per-node or time-windowed, rather than fixed 100-line) would likely shrink the random-vs-chronological gap by reducing near-duplicate windows straddling any split — worth testing before more modeling effort.
4. **A capacity-matched, instruction-tuned check** — since bigger (3B) made calibration worse, not better, in this comparison, a like-for-like next step is testing whether a differently-instruction-tuned 1B/3B model changes the specific "retrieves fact, ignores rule" failure mode, before assuming LoRA is the only fix.
5. **Refresh `docs/ROADMAP.md`/`docs/RESEARCH_POSITIONING.md`** to reflect that BGL generalization is now tested (not "registry ready but untested") and to fold in this phase's honest caveats.
